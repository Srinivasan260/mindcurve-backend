Quiz logic — deep dive

Reference · 2026-11-19 · Athma backend

Everything that happens between a patient clicking “Start assessment” and the backend persisting a final risk level. Covers the data model, the three scoring recipes, how reverse-scoring is applied (and why it’s applied at answer time, not at submit), how risk bands are looked up, and how “high risk” is flagged for triage. Every mechanism has a flowchart and a worked example with real numbers.

2. Data model — 6 tables

The quiz uses six tables. Four of them are configuration set up by admins; two of them are runtime rows written as a patient takes the quiz.

TablePurposeWritten byKey fields
categories One category = one “assessment” (e.g. BDI, BFI-10). Holds the scoring recipe. Admin scoring_type ∈ { total, subscale_sum_cutoff, subscale_mean_band }
questions Prompt text + metadata. Admin subscale (nullable), is_reverse_scored (bool), display_order
question_options 2–7 answer choices per question, each with a numeric score. Admin score (int), display_order
category_risk_bands Score-range → risk-level lookup table. Admin subscale (nullable — see below), level, min_score, max_score
assessments One attempt by one patient at one category. Runtime (patient) status, overall_risk_level, started_at, completed_at
answers One row per answered question. Stores the already-flipped score. Runtime (patient) score_snapshot — the final, scorable value
assessment_category_results Computed output. One row per subscale (plus optional overall). Runtime (submit) subscale (null means “whole quiz”), total_score, risk_level
Why score_snapshot instead of joining to the option every time? Snapshot semantics: if an admin edits an option’s score tomorrow, old assessments do not silently rewrite themselves. The historical record stays accurate.

The subscale column is the whole trick

One column — subscale — appears on questions, category_risk_bands, and assessment_category_results. It’s nullable, and that nullability is load-bearing:

  • On a questions row: null = the question contributes to the single whole-quiz score. A string like "extraversion" = the question belongs to that subscale only.
  • On a category_risk_bands row: null = this band matches the whole-quiz total. "overall" = the aggregate row in Recipe B. A subscale name = a cutoff for that subscale.
  • On a assessment_category_results row: null = the single result for a Recipe-A category. A string = per-subscale result for Recipe B or C.

3. Quiz lifecycle — 3 endpoints

#EndpointService methodWhat changes in the DB
1 POST /categories/:categoryId/assessments assessmentService.start Insert into assessments (status=in_progress) OR return the existing in-progress row.
2 POST /assessments/:id/answers  loop assessmentService.submitAnswer Upsert into answers. Reverse-scoring applied before write.
3 POST /assessments/:id/submit assessmentService.submit Read all answers → dispatch recipe → write N rows to assessment_category_results → flip status=completed. All in one Prisma $transaction.

4. Step 1 — starting an assessment

Guards before creating a new row:

  1. Category must exist AND be is_active=true → else 404.
  2. Caller must own a patient_profiles row (not just a users row) → else 403.
  3. If an in_progress assessment for this patient + category already exists, resume it rather than inserting a duplicate.
Guards and the resume-vs-create decision in assessmentService.start.

Every start/resume also writes an activity_log row (assessment_started or assessment_resumed) so the admin dashboard can show a live feed.

5. Step 2 — submitting each answer

Called once per question. It’s idempotent: the body carries questionId and selectedOptionId, and the repository uses a Prisma upsert keyed on (assessmentId, questionId). A patient can therefore change their mind freely until they hit submit — each call replaces the previous selection and refreshes score_snapshot + answered_at.

Validation in order

  1. Patient profile exists → else 403.
  2. Assessment belongs to this patient → else 404.
  3. Assessment is still in_progress → else 409 (locked after submit).
  4. The selected option really belongs to the stated question AND the question belongs to this assessment’s category AND the question is is_active → else 422. This is the one query that stops cross-category or deactivated-question attacks.

What gets stored

answers {
  assessmentId,
  questionId,
  selectedOptionId,
  score_snapshot   // ← already reverse-flipped if is_reverse_scored
}

6. Reverse scoring — the formula

Some psychometric instruments include questions whose answer scale runs the opposite direction from the rest. On the BFI-10, for example, “I see myself as someone who is reserved” is reversed because agreement means less extraversion, not more. The flip is a mirror around the midpoint of the option range.

The code

// assessment.service.ts
let scoreSnapshot = option.score;
if (option.question.isReverseScored) {
  const scores = option.question.options.map(o => o.score);
  const maxS = Math.max(...scores);
  const minS = Math.min(...scores);
  scoreSnapshot = maxS + minS - option.score;
}

The formula

Given a question whose options span scores [min, max]:

flipped = max + min − raw

Worked example — 5-point Likert, options 1…5

Patient picksraw scoremax+minflipped
Strongly disagree15+1 = 65
Disagree264
Neutral363
Agree462
Strongly agree561

Perfect mirror. The midpoint (3) is its own reflection. And it works for non-symmetric ranges too: options 0…3 give max+min = 3, so 0→3, 1→2, 2→1, 3→0.

Why it’s applied at answer time, not at submit

Snapshot semantics. If an admin flips is_reverse_scored on a question after some patients have answered it, their historical answers do not retroactively re-score. The flip is baked into score_snapshot at the moment of answering and never reconsidered. This mirrors how option.score edits also don’t rewrite history.
Reverse scoring branches before the DB write, so score_snapshot is always the final value.

7. Step 3 — finalising the assessment

The patient has answered everything and now calls POST /assessments/:id/submit. The service does five things in order, the last three inside one Prisma transaction:

  1. Load every answer with its question’s subscale.
  2. Load every category_risk_bands row for the category. (Prisma returns min_score/max_score as Decimal; we cast to number so plain arithmetic works.)
  3. Dispatch on category.scoring_type to one of three pure functions. Each returns an array of { subscale, totalScore, riskLevel }.
  4. Inside a transaction: update the assessment (status=completed, completed_at, overall_risk_level) → delete any stale results rows for this assessment → bulk-insert the new ones.
  5. Write an activity_log row — flagged_high_risk if any result is high/flagged/severe, else assessment_completed.
overall_risk_level is only set for Recipe A. For subscale-based recipes there’s no single “overall” number that admins would trust, so the column stays null and the detail view shows per-subscale rows instead.

8. Recipe A — total

Simplest of the three. Sum every score_snapshot, then find the single band row (one where subscale IS NULL) whose range contains the sum.

Pseudocode

total = Σ answers.score_snapshot
matched = bands
  .filter(b => b.subscale === null AND total ∈ [b.min_score, b.max_score])
  .sort(desc by min_score)[0]
return [{ subscale: null, totalScore: total, riskLevel: matched?.level ?? 'moderate' }]

Sorting by min_score descending acts as a tie-breaker: if two bands overlap (which shouldn’t happen but we don’t enforce it in the DB), the one with the higher floor wins. In practice admins define non-overlapping ranges.

Worked example — PHQ-9 style (9 questions, options 0…3)

Patient answers: scores 3, 2, 3, 2, 1, 3, 2, 3, 2. Sum = 21.

Result: single row with riskLevel = 'severe'. Because the scoring type is total, this also becomes assessments.overall_risk_level = 'severe', and the activity log entry is flagged_high_risk (see §11).

9. Recipe B — subscale_sum_cutoff

Used when each subscale has an independent cutoff: hit the threshold on any of them and you’re flagged, regardless of the others. (Think: a screener where elevated anxiety OR elevated depression OR elevated panic each qualifies for follow-up.)

Pseudocode

// 1. bucket answers by subscale
bySubscale = groupBy(answers, a => a.question.subscale)   // ignores answers with no subscale

for each (subscale, group) in bySubscale:
  sum = Σ group.score_snapshot
  subBands = bands.filter(b => b.subscale === subscale)
  matched = subBands
    .filter(b => sum ∈ [b.min_score, b.max_score])
    .sort(desc by min_score)[0]
  emit { subscale, totalScore: sum, riskLevel: matched?.level ?? 'normal' }

// 2. aggregate "overall" row
overallSum = Σ ALL answers.score_snapshot
overallBands = bands.filter(b => b.subscale === 'overall' OR b.subscale === null)
match overallSum against overallBands → emit { subscale: 'overall', ... }
The convention. A band row whose subscale matches a real subscale name acts as a cutoff: if the patient’s sum lands in its [min, max] range, that band’s level wins (typically flagged). Otherwise we default to normal.

Worked example — Psychotic-screening style, 3 subscales

Admins configured the bands below. flagged is the cutoff on each subscale; the 'overall' band aggregates everything for a dashboard-friendly summary.

10. Recipe C — subscale_mean_band

The “benchmark” recipe. Each subscale gets a mean (not a sum) and that mean is bucketed into a named band. Typical of personality inventories where every subscale produces a comparable score (e.g. BFI-10: five traits, mean of 1…5 per trait).

Pseudocode

bySubscale = groupBy(answers, a => a.question.subscale)

for each (subscale, scores) in bySubscale:
  mean = Σ scores / scores.length
  applicable = bands.filter(b => b.subscale === subscale OR b.subscale === null)
  matched = applicable.find(b => mean ∈ [b.min_score, b.max_score])
  emit { subscale, totalScore: mean, riskLevel: matched?.level ?? 'moderate' }
No overall row is computed for Recipe C — each subscale is independently meaningful and averaging subscales would be misleading. The applicable filter accepts bands with subscale IS NULL as well, so admins can define one shared low/medium/high ladder instead of repeating it per trait.

Worked example — BFI-10 (Extraversion, 2 questions, options 1…5)

Question 1 ("I see myself as outgoing", not reversed): patient picks 4.
Question 2 ("I see myself as reserved", is_reverse_scored=true): patient picks 2.

Reverse flip on Q2: max+min − raw = 5+1 − 2 = 4. So both score_snapshots are 4.

Mean for Extraversion = (4 + 4) / 2 = 4.0.

11. High-risk flagging

After the results are written, the service inspects them to decide which activity_log action to write. This is the signal the admin dashboard uses to surface at-risk patients in its live feed. 

const hasHighRisk = results.some(r =>
  r.riskLevel === 'high' ||
  r.riskLevel === 'flagged' ||
  r.riskLevel === 'severe'
);

activity_log.action = hasHighRisk
  ? 'flagged_high_risk'
  : 'assessment_completed';

The three magic strings are intentionally duplicated across recipes so admins can choose the vocabulary that fits each instrument:

  • severe — usual label for Recipe A clinical screeners (PHQ-9’s top band).
  • flagged — usual label for Recipe B cutoff bands.
  • high — usual label for Recipe C personality benchmarks.
The activity_log metadata also carries a copy of every { subscale, totalScore, riskLevel } tuple, so the dashboard can render a one-line summary without re-reading the results table.

12. Edge cases & failure modes

What if no band matches the computed score?

Each recipe has a documented fallback, and Recipe A also emits a logger.warn so it shows up in the server logs. These defaults exist so an admin’s misconfiguration (e.g. gap between bands) doesn’t 500 the request — the patient still gets some result.

  • Recipe A → moderate + warning log.
  • Recipe B per-subscale → normal (quiet).
  • Recipe B overall → normal (quiet).
  • Recipe C → moderate (quiet).

What if the patient re-submits an answer for the same question?

The repository uses prisma.answer.upsert keyed on the unique (assessmentId, questionId) pair. Second answer wins. answered_at is refreshed to the new timestamp.

What if the patient tries to submit twice?

Second call gets 409 Conflict because the status is no longer in_progress. There’s no “un-submit” endpoint — the result is immutable from the patient’s side. Admins can inspect historical answers via GET /admin/assessments/:id.

What if an admin edits a question option’s score after some answers exist?

Historical answers are unaffected — they stored score_snapshot at answer time. New answers written after the edit will pick up the new score. This is a feature, not a bug: without snapshot semantics you’d have to recompute every past assessment on every config change.

What if an admin flips is_reverse_scored after some answers exist?

Same answer: historical answers keep their flipped-or-not state as stored. The flag only affects answers written after the flip.

What if a patient submits with zero answers?

Submit still succeeds. Recipe A produces total = 0, which falls into whatever band owns 0 (or the moderate default). Recipes B and C produce zero result rows because there are no subscales to group by (plus the Recipe B overall row with sum = 0). The UI is responsible for preventing this state from the patient’s side.

What if the category changes scoring_type between start and submit?

Submit reads assessment.category.scoringType fresh at submit time, so the new recipe runs. In practice admins shouldn’t change scoring_type on a live category — the Zod validation on the admin update endpoint can’t forbid this but the UI should warn.
