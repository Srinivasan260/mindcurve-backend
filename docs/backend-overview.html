1. The 30-second overview

Athma is a mental-health assessment platform with two audiences served by one backend:

  • Patients register themselves, verify their email via a magic link, pick a category (like Depression Screening or BFI-10 Personality), answer a set of questions, and get a risk-level result.
  • Admins / doctors configure the categories + questions + scoring thresholds, review every patient's assessment, add clinical notes, schedule follow-ups, and monitor a live dashboard of KPIs and activity.

The backend is a single REST API served on http://localhost:5000/api/v1 with interactive docs at http://localhost:5000/api/docs (Swagger UI).

/admin/auth/*Admins / doctorsPOST /admin/auth/login
/admin/*Admins / doctors only (JWT role-gated)GET /admin/dashboard/summary

The 5 files in every module

FileRole
<feature>.validation.tsZod schemas (one per endpoint). Also exports the inferred TS types.
<feature>.repository.tsThe only file that calls Prisma. Returns raw rows.
<feature>.service.tsBusiness logic. Calls the repo, throws ApiError on failure.
<feature>.controller.tsThin HTTP wrapper. Parses req, calls the service, shapes the response.
<feature>.route.tsWires URL → middleware → controller. Holds @openapi JSDoc blocks.

Admin-only endpoints in a module live in a second file <feature>.admin.route.ts. Both are mounted from routes.ts under the appropriate prefix.

4. Auth model

Two login doors, same backend. Each one only accepts users whose role matches that door.

EndpointAllowed rolesOn mismatch
POST /auth/loginpatientAdmin accounts → 403 "Admin accounts must use the admin login page."
POST /admin/auth/loginadmin, doctorPatient accounts → 403 "Patient accounts must use the regular login page."

Both return the same LoginResponse shape: { token, user }. The only difference is the role-gate.

End-to-end request flow

  1. User logs in (or clicks a magic link) → backend issues a JWT signed with JWT_SECRET, valid for JWT_EXPIRES_IN (default 7 days).
  2. JWT payload: { sub: userId, email, role, iat, exp }.
  3. Frontend stores the JWT.
  4. Every subsequent request sends it: Authorization: Bearer <token>.
  5. The requireAuth middleware verifies the signature and attaches req.user.
  6. requireRole('admin', 'doctor') checks req.user.role and returns 403 on mismatch.

Magic-link email verification

  1. On registration, user is created as is_email_verified=false.
  2. Backend generates a 64-char token → stores only the SHA-256 hash in email_tokens.
  3. Emails the user a link: {APP_URL}/auth/magic-login?token=<raw>.
  4. Patient clicks → frontend POSTs the token to /auth/magic-login.
  5. Backend hashes it, verifies not-used + not-expired, then atomically marks used, flips is_email_verified=true, bumps lastLoginAt, issues JWT.
If SMTP isn't configured in .env, the magic link is logged to the console — the dev loop still works end-to-end without a mail provider.

5. Patient journey — step by step

#Patient actionEndpointBackend does
1Fills registration formPOST/auth/registerCreates user (unverified) + patient_profile in a transaction; generates magic-link token; emails it
2Clicks magic linkPOST/auth/magic-loginHashes token, validates it, marks used, flips is_email_verified=true, issues JWT
3(Returning) email + password loginPOST/auth/loginVerifies password, issues JWT (patient role only)
4Sees available assessmentsGET/categoriesReturns only active categories + question count
5Picks a category, startsPOST/categories/:categoryId/assessmentsCreates assessment row; rejects duplicates with 409
6Sees the questionsGET/categories/:categoryId/questionsReturns questions + options with scores hidden to avoid bias
7Answers each questionPOST/assessments/:id/answersUpserts answer; snapshots the score (applies reverse-scoring here); idempotent
8SubmitsPOST/assessments/:id/submitPicks scoring recipe from category; writes per-subscale results[]; marks completed; logs activity
9Views resultGET/assessments/:idReturns assessment with answers + per-subscale results
10Reviews past assessmentsGET/assessmentsLists own assessments; supports ?status, ?categoryId

Key guarantees

  • A patient cannot access another patient's assessments — every query filters by patientId from the JWT.
  • scoreSnapshot is immutable — admin edits to option scores never change historical answers.
  • Reverse scoring happens at answer time, not submit time — the stored snapshot is already the final value.

8. The 3 scoring recipes

Every category carries a scoringType. On submit, the service dispatches to one of three recipes.

Recipe A · total (ISAA-style)

One grand total → one risk band. No subscales, no reverse scoring.

QuestionChosen optionScore
Q1Frequently3
Q2Mostly4
Q3Always5
Total12

Look up the matching band where min_score ≤ 12 ≤ max_score and subscale IS NULL. One row written, subscale=NULL.

Recipe B · subscale_sum_cutoff (SCARED-style)

Group by subscale → sum each → compare to that subscale's cutoff. Also writes an overall row.

QuestionSubscaleScore
Q1panic2
Q6panic2
Q5generalized2
Q7generalized2
SubscaleSumCutoffRisk level
panic4≥ 7normal
generalized4≥ 9normal
overall8≥ 25normal

Recipe C · subscale_mean_band (BFI-10-style)

Reverse-score flagged questions → group by subscale → take the mean → look up benchmark band.

Reverse-scoring happens at answer time with scoreSnapshot = (max + min) - raw. For a 1–5 Likert scale that's 6 − raw.

QuestionRaw answerReverse?Final score
Q1 "I see myself as reserved"4 (Agree a little)Yes → 6−42
Q6 "I see myself as outgoing"2 (Disagree a little)No2

Mean = (2 + 2) / 2 = 2.0

RangeBand
4.5 – 5.0Very High
3.5 – 4.4High
2.5 – 3.4Average
1.5 – 2.4Low ← matches 2.0
1.0 – 1.4Very Low

Result: one row with subscale="extraversion", totalScore=2.0, riskLevel="low".

Why the distinction matters

Scoring typeReverse scoringScore shapeOutput rowsOverall risk?
totalNoInt sum1 (subscale=NULL)Yes — set on assessment
subscale_sum_cutoffNoInt sums per subscaleN+1 (per subscale + overall)No
subscale_mean_bandYes (per question)Decimal meansN (one per trait)No

9. Database schema

MySQL 8, utf8mb4_0900_ai_ci collation, all PKs are CHAR(36) UUIDs. Managed by Prisma.

Tables

TablePurpose
usersAuth record (email, password hash, role, verified, active, lastLoginAt)
patient_profiles1:1 extension of users for patients (name, phone, demographics, consent)
email_tokensHashed magic-login / password-reset tokens; used-once with expiry
categoriesAssessment categories. Carries scoringType.
category_risk_bandsScore ranges → risk labels, per category and (optionally) per subscale
questionsQuestions in a category. Carries subscale + isReverseScored
question_options2–7 options per question, each with a score
assessmentsOne row per patient × category attempt (in_progress / completed / abandoned)
answersPatient's chosen option per question. Carries immutable scoreSnapshot.
assessment_category_resultsPer-subscale results computed on submit
clinical_notesFree-text notes from admin/doctor on a patient
follow_upsAdmin queue of callbacks to make for patients
activity_logsAppend-only audit of important events (feeds the dashboard feed)

assessments (1) ─── (*) follow_ups         (optional link)

Design decisions worth knowing

  • scoreSnapshot on answers — captured at answer time. Admin edits to option scores never change historical answers.
  • Reverse scoring at answer time — the stored snapshot is already the final, flipped value.
  • minScore / maxScore are DECIMAL(10,4) — supports both integer sums and decimal means like 1.5–2.4.
  • Email tokens store SHA-256 hashes only — if the DB leaks, nobody can hijack active magic links.
  • Result uniqueness is (assessment_id, category_id, subscale) — lets subscale-based tests write multiple result rows per assessment.

10. Local setup

Prerequisites

  • Node 20+ and npm 10+
  • MySQL 8 running locally

First-time setup

  1. cd backend && npm install
  2. Copy .env.example → .env and fill MySQL credentials + JWT_SECRET
  3. Create the DB: mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS MentalHealthInventory CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
  4. Apply migrations: npx prisma migrate deploy
  5. Generate the typed client: npx prisma generate

Seed an admin user (SQL)

Generate a bcrypt hash first:

node -e "const bcrypt=require('bcrypt'); bcrypt.hash('Admin@123',12).then(h=>console.log(h))"

Then insert in MySQL:

INSERT INTO users (id, email, password_hash, role, is_email_verified, is_active, created_at, updated_at)
VALUES (
  UUID(),
  'admin@athma.com',
  '<paste hash here>',
  'admin', 1, 1, NOW(), NOW()
);

Run

  • Dev (hot-reload): npm run dev
  • Typecheck: npm run typecheck
  • Build: npm run build → dist/
  • Prod: npm start
  • Prisma Studio (GUI): npx prisma studio
